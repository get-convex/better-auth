## Upgrade

<div className="fd-steps">

  <div className="fd-step">

### Install dependencies

Update Better Auth and the component. Better Auth must be on `1.7.7` or later in
the `1.7.x` line. Update any installed `@better-auth/*` packages together.

```npm
npm install @convex-dev/better-auth@^0.13.0
npm install better-auth@~1.7.7
```

<Callout>
  Review the [Better Auth 1.7 upgrade
  guide](https://www.better-auth.com/docs/guides/1-7-upgrade-guide) and [1.7.7
  release notes](https://github.com/better-auth/better-auth/releases/tag/v1.7.7)
  for the features your app uses.
</Callout>

  </div>

  <div className="fd-step">

### Check existing accounts

Accounts still use `(providerId, accountId)`, as in 1.6. **No issuer backfill is
needed.** Check for duplicate pairs before upgrading; Better Auth now rejects
ambiguous account lookups. Resolve duplicates using trusted provider data and
keep different users separate. Credential accounts should have `accountId` equal
to `userId`.

If you tested 1.7.0–1.7.2, see [Early 1.7 deployments](#early-17-deployments)
below. Microsoft accounts have a separate migration described below.

  </div>

  <div className="fd-step">

### Deploy and test

Back up your data and test the upgrade on a development deployment first.
Regenerate Convex bindings, then deploy the component and application changes
together. Verify sign-in, existing sessions, account linking, token refresh, and
`/api/auth/convex/jwks` for the features you use.

Upgrade servers sharing verification storage and OAuth Proxy participants
together. Request fresh Magic Links and restart pending OAuth/SAML sign-ins
after deploying, as required by the 1.7.7 security fixes.

## Breaking changes

### Account selectors

Read the local account `id` from `listAccounts` and pass it as `accountId` to
`unlinkAccount`. For `getAccessToken`, `refreshToken`, and `accountInfo`, pass
exactly one of `{ accountId: account.id }` or `{ useAccountCookie: true }`.
Remove `providerId` from these selectors. Cookie selection requires
`account.storeAccountCookie` in your Better Auth configuration.

### Generic OAuth

Use the standard social client APIs:

```ts
await authClient.signIn.social({ provider: "my-provider" });
await authClient.linkSocial({ provider: "my-provider" });
```

These replace `signIn.oauth2()` and `oauth2.link()`. Remove
`genericOAuthClient()` and change provider callback URLs from
`/api/auth/oauth2/callback/:id` to `/api/auth/callback/:id`.

### Microsoft accounts

Microsoft accounts now use `oid` instead of `sub`, including the Generic OAuth
Microsoft Entra helper. Pause Microsoft sign-in and linking while updating
stored account IDs from verified ID tokens or a trusted Entra export. The old
account row alone cannot supply this mapping.

The Generic OAuth `microsoftEntraId` helper requires a concrete tenant GUID and
an `id_token` from the token exchange. Use the built-in Microsoft provider for
`common`, `organizations`, or `consumers`. Follow the upstream guide's
[Microsoft migration steps](https://www.better-auth.com/docs/guides/1-7-upgrade-guide#migrate-microsoft-account-identifiers).

### Database joins

Move `experimental.joins` to `advanced.database.joins`. The Convex adapter
continues to disable native joins and use its existing relation queries.

## Early 1.7 deployments

Better Auth 1.7.3 removed the required `issuer` field introduced in 1.7.0–1.7.2.
The bundled component keeps it optional to accept existing data, but no longer
includes issuer indexes or backfill functions.

For Local Install, remove issuer-based constraints and indexes. Keep `issuer`
optional until stored values are removed. If different issuers shared one
provider ID and overlapping account IDs, assign distinct provider IDs and update
the matching account rows before resuming sign-in.

## OAuth or OIDC provider

Only follow this section if your app used `oidcProvider` to act as an identity
provider. Apps that only sign in through an external provider can skip it.

### Export and clear legacy records

Back up your data and pause authentication writes and public HTTP routes during
the conversion. Keep the bundled component mounted until export and cleanup are
complete. Add these internal wrappers:

```ts title="convex/migrations.ts"
import { v } from "convex/values";
import { internalMutation, internalQuery } from "./_generated/server";
import { components } from "./_generated/api";

export const listLegacyOAuthApplications = internalQuery({
  args: { cursor: v.union(v.string(), v.null()) },
  handler: async (ctx, { cursor }) => {
    return await ctx.runQuery(
      components.betterAuth.migrations.listLegacyOAuthApplications,
      { paginationOpts: { cursor, numItems: 100 } }
    );
  },
});

export const clearLegacyOAuthProviderRecords = internalMutation({
  args: {
    table: v.union(
      v.literal("oauthApplication"),
      v.literal("oauthAccessToken"),
      v.literal("oauthConsent")
    ),
    cursor: v.union(v.string(), v.null()),
  },
  handler: async (ctx, { table, cursor }) => {
    return await ctx.runMutation(
      components.betterAuth.migrations.clearLegacyOAuthProviderRecords,
      { table, paginationOpts: { cursor, numItems: 100 } }
    );
  },
});
```

Export every page of client registrations and save the results securely. The
export omits `clientSecret`; review custom `metadata` before reusing it.

```bash
npx convex run migrations:listLegacyOAuthApplications '{"cursor":null}'
```

After verifying the export, clear the old tokens, consents, and applications in
that order. This invalidates existing provider tokens and removes client
secrets.

```bash
npx convex run migrations:clearLegacyOAuthProviderRecords \
  '{"table":"oauthAccessToken","cursor":null}'
npx convex run migrations:clearLegacyOAuthProviderRecords \
  '{"table":"oauthConsent","cursor":null}'
npx convex run migrations:clearLegacyOAuthProviderRecords \
  '{"table":"oauthApplication","cursor":null}'
```

For each command, pass the returned `continueCursor` to the next call until
`isDone` is true. A completed cursor is terminal; use `null` only to start a new
pass. Add `--prod` when running against production.

### Switch to Local Install

1. Follow the [Local Install guide](/local-install). Keep the component mounted
   as `betterAuth` so existing data stays under `components.betterAuth`.
2. Install `@better-auth/oauth-provider@~1.7.7` and replace `oidcProvider()`
   with `jwt()` and `oauthProvider()` in your static Better Auth options. Follow
   the upstream
   [provider migration guide](https://www.better-auth.com/docs/guides/1-7-upgrade-guide#as-an-identity-provider).
3. Generate the new schema after adding the plugin and clearing all three legacy
   tables. Retain optional `account.issuer` if existing records still contain
   it.
4. Deploy while writes remain paused. Confirm that existing users, accounts, and
   sessions remain under the same component mount before proceeding.
5. Re-register exported clients. Map `redirectUrls` to `redirectUris`, parse
   legacy `metadata` as JSON, and review grant types and token authentication.
   Distribute new client secrets and issue new provider tokens.
6. Test authorization, consent, token issuance, refresh, user info, and logout
   before restoring traffic. Restore the backup with the old application version
   if the conversion fails.

## Local Install additional steps

Generate the 1.7.7 schema to a side file and compare it with your deployed
schema:

```npm
cd convex/betterAuth
npx auth generate --output generatedSchema.next.ts
```

Preserve custom fields and indexes. Include the generated credential lookup
index `userId_providerId_accountId` on `["userId", "providerId", "accountId"]`
and export `incrementOne` with your other adapter functions. The adapter
implements `consumeOne` using the component's atomic `deleteOne`.

If you already use Local Install with `oidcProvider`, implement local
equivalents of the export and cleanup helpers above. During export, retain
`oauthApplication` and merge legacy/new `oauthAccessToken` and `oauthConsent`
fields as optional unions. Clear legacy records before applying the final
provider schema.
